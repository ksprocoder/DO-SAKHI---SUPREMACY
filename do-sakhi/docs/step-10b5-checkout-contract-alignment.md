# Step 10B.5: Checkout Payload Contract Alignment + Backend Cart Sync QA

## 1. Executive Summary
Step 10B.5 is complete. The contract problem between the frontend localStorage cart and the backend checkout API has been fully resolved. The frontend and backend are now perfectly aligned. The backend `create-payment-order` API correctly accepts the exact item array format generated by the frontend, validates against the database, checks stock, and securely creates the Razorpay test order.

## 2. Contract Problem Investigated
The backend originally expected a single `cartId` string to fetch cart items from the `cart_items` table. However, the frontend cart built in Steps 7-9 is entirely driven by `localStorage` (`CartProvider`) and does not interact with the backend `carts` or `cart_items` tables. Because the frontend didn't have a backend `cartId` to pass, checkout would fail immediately.

## 3. Frontend Cart Source of Truth
The frontend source of truth is purely local state hydrated from `localStorage`. The `CartProvider` tracks `productId`, `variantId`, `quantity`, and any `tailoringProfile` selected by the customer.

## 4. Backend Payment Source of Truth
To remain secure, the backend does **not** trust any prices sent from the frontend. The backend accepts `productId` and `variantId`, and performs a `SELECT ... FOR UPDATE` query against the `product_variants` and `products` tables to fetch the authoritative `price_inr` and `stock_quantity`.

## 5. Chosen Architecture
**Option C: Backend create-payment-order Accepts Frontend Items** was chosen.
Why: This is the safest and cleanest approach for a luxury boutique MVP. It avoids building a complex and brittle invisible cart-syncing layer. The frontend simply hands off the user's visible intention (the items and custom measurements) to the backend checkout endpoint, which acts as the ultimate authority on pricing and availability.

## 7. Backend Validation and Amount Recalculation
- **Zod Validation**: Ensures data structure integrity (e.g., UUIDs, positive integers).
- **Price Authority**: Backend loops over the submitted `items` and queries `product_variants.price_inr`.
- **Total Calculation**: `totalAmountInr += (Number(variant.price_inr) * item.quantity)`. No floating-point rounding errors.

## 8. Tailoring Data Contract
Custom tailoring details are captured securely from `item.tailoringProfile`. If present, the backend inserts a corresponding row into the `custom_tailoring_details` table, correctly linked to the new `order_items` row.

## 9. Stock and Reservation QA
- **Locking**: `SELECT ... FOR UPDATE` prevents race conditions.
- **Validation**: Checks `quantity <= (stock_quantity - reserved_quantity)`.
- **Reservation**: `reserved_quantity` is immediately incremented upon order creation.
- **Failure Safety**: If Razorpay test order creation fails, reserved quantities are cleanly reverted.

## 10. Payment Config QA
- `PAYMENTS_ENABLED=false`: Fails safely with `PAYMENTS_DISABLED` without breaking local app flow.
- `PAYMENTS_ENABLED=true` + no keys: Fails safely with `PAYMENTS_NOT_CONFIGURED`.
- `RAZORPAY_ENV=test`: Permitted.
- `RAZORPAY_ENV=live`: Allowed strictly conditionally based on environment variables (but test-mode handles current flow).
